# 0004 — Place a solid box's rect from its corners rather than assuming a y-flipping view transform

**Status:** Open
· **Kind:** Bug
· **Parent:** <a href="README.md" title="Issues">Issues</a>
· **Related:** <a href="0003.md" title="0003 — Decide whether `Decal.xform` or the renderer is the real transform API">0003</a>

> A solid `BoxDecal` renders as an SVG `rect` whose origin is taken from
> `corners[3]`. That is the minimum-`y` corner only after a transform that
> inverts `y`. Under any other view transform the rect lands somewhere the box
> is not — under the identity, two units off for a default centred box.
>
> The demo has never been in the wrong case, because `App.jsx` builds its view
> transform as `mat3.scaling(scale, -scale)`. So this is latent rather than
> visible, and it is exactly the kind of thing that stops being latent the first
> time someone renders a scene to a non-flipped target.

## Background

Raised during review of [#14](https://github.com/kkroening/physm/pull/14). The
code is carried across verbatim from `BoxDecal.getDomElement`, so it predates
that change; the move is only what made it visible.

Under `mat3.IDENTITY`, a default centred `BoxDecal({ width: 4, height: 2 })`:

```
corners     = [(-2,-1), (2,-1), (2,1), (-2,1)]
corners[3]  = (-2, 1)
=> <rect x=-2 y=1 width=4 height=2 />   spans y in [1, 3]
   the box itself                        spans y in [-1, 1]
```

Under `mat3.scaling(1, -1)` the corner order reverses, `corners[3]` becomes
`(-2, -1)`, and the rect lands on the box.

Two more consequences of the same construction, both also pre-existing:

- **A solid box ignores its `angle`.** The rect is axis-aligned `width` by
  `height`, so a rotated solid box renders unrotated. Only the outlined branch,
  which draws the corners as four lines, respects rotation.
- **A non-uniform view scale sizes it wrongly.** `scaleFactor` is
  `sqrt(|det|)`, one number for both axes.

The test does not catch any of it: `draws a solid box as one rect` uses the
identity transform and asserts `width` and `height` only, so it passes against a
rect drawn two units off. The reflection test that does exercise corner order
takes the `solid: false` branch.

## Proposal

Two candidate fixes, and the second disposes of more:

1. **Pick the origin by `Math.min`** over the transformed corners rather than by
   index, which removes the dependence on corner ordering and therefore on the
   sign of the transform. Still leaves the rotation and non-uniform-scale gaps.
2. **Emit a `<polygon>`** with the four transformed corners. There is then no
   origin corner to choose, no axis-aligned assumption, rotation works, and the
   solid and outlined branches draw the same four points by the same path.

`<polygon>` looks right, and is a visible output change rather than a refactor —
which is why it was not folded into #14, whose evidence was that the rendered
SVG stayed byte-identical.

## Acceptance

A solid box renders in the right place under the identity transform, under a
`y`-flip, and rotated — with `x`/`y` asserted in the test rather than implied,
so the choice is pinned rather than left to the fixture's transform.
