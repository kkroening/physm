# 0015 — Decide whether physm-js declares a surface, and run the dead-code check against it

**Status:** Open
· **Kind:** RFC
· **Parent:** <a href="README.md" title="Issues">Issues</a>
· **Related:** <a href="0010.md" title="0010 — Make a dead export a build signal rather than an eyeball finding">0010</a>

> The dead-code check from [0010](0010.md) treats every test file as an entry
> point, so a module kept alive only by its own test passes. That is 39 of the
> 68 modules under `src/`. Closing it means running the check in production
> scope — and the first thing that reports is the React binding's own barrel.

## Background

`knip` counts a test file as a consumer, so `src/foo.ts` imported by nothing
but `src/foo.test.ts` is reachable and reports clean. For the 39 modules with a
sibling test, a green step therefore means "not even its own test imports this"
rather than "something uses this". The leftover it cannot see is a dead module
plus a test that exercises nothing.

`knip --production` is the answer to that, and on the tree as it stands it
reports two files:

- **`src/react/index.ts`** — the React binding's barrel, which opens
  ``  `physm/react` — the React binding `` and re-exports the components by
  name. It is imported today only from `CartAndRope.test.tsx` and
  `emitScene.test.tsx`. So the one declared surface this package has is
  consumed by nothing but tests.
- **`src/setupTests.js`** — vitest's setup file, reached through
  `vite.config.js` rather than by an import. Configuration rather than a
  finding.

The first is the real question, and it is why this is an RFC rather than a
patch. That barrel is a partial statement of what the package publishes: it
covers `src/react`, and it re-exports *values* and not the props types beside
them. There is nothing equivalent for the core modules, and no `exports` map in
`package.json` narrower than the whole tree. So the package half-declares a
surface, for half of itself, and nothing outside a test reads it.

Note what this issue is *not* about any more. When it was filed it was largely
about fifty-one export findings; that count came from knip 5, and knip 6 —
the pinned version — reports none once the twelve genuine over-exports are
un-exported, which [0010](0010.md) did. Exports, types and duplicates are all
in scope today and the tree is clean.

## What to decide

- **Whether the package declares a surface at all**, or is a tree of modules an
  application imports from directly. Both are legitimate. If the second, the
  barrel is itself the dead code and should go, and the check stays
  test-inclusive permanently.
- **If it does declare one: where, and covering what.** The barrel is a worked
  precedent for one of the three usual answers — an index module, an `exports`
  map, or a convention plus a knip `entry` list — and it has already made the
  values-not-types choice once. Whether the core modules get the same treatment
  is the other half.
- **Whether a production-scoped pass runs in CI**, given that it is the only
  thing that would catch the next `testutils.ts` that happens to have a test.

## Acceptance

What the package publishes is written down, and the dead-code check's scope
follows from that decision — widened to production scope with the surface
declared as its entry points, or deliberately left test-inclusive with the
reason recorded where the next reader will find it.
