# 0015 — Decide what physm-js publishes, so a dead export can be told from a published one

**Status:** Open
· **Kind:** RFC
· **Parent:** <a href="README.md" title="Issues">Issues</a>
· **Related:** <a href="0010.md" title="0010 — Make a dead export a build signal rather than an eyeball finding">0010</a>

> The dead-code check added by [0010](0010.md) is scoped to files rather than
> exports, because nothing in the package says which exports are its public
> surface. Pointed at exports it reports fifty-one findings, and most of them
> are not defects — they are the API.

## Background

`knip` run against `physm-js` with exports included reports:

- **45 unused exported types**, of which most are React props interfaces —
  `BoxProps`, `CircleProps`, `SceneProps`, `WeightProps` and their siblings.
  Nothing inside the package imports them, and that is expected: they exist so
  that a consumer can type a wrapper around a component. The same is true of
  the options interfaces on the core classes (`SceneOptions`,
  `JsSolverOptions`, `TrackFrameOptions`).
- **6 unused exported values** — `consistencyTolerance`, `planarDeterminant`,
  `isValidStateMap`, `SingularCorrectionError`, and `daglet`'s
  `defaultGetNodeParents` and `defaultGetNodeKey`. These are *not* unreferenced:
  each is used inside its own module. They are over-exported rather than dead,
  which is a milder and more interesting finding.

Both lists are the same question wearing two hats. `SingularCorrectionError` is
plausibly something a consumer catches; `planarDeterminant` is plausibly an
internal of `Mat3`. Nothing distinguishes them today, because the package has no
statement of what it publishes: there is no index module, no `exports` map
narrower than the whole tree, and no convention that says "exported from here
means public".

Until there is, a check pointed at exports cannot tell an API from an orphan,
and would have to be argued with on nearly every finding — the failure
[0010](0010.md) explicitly set out to avoid.

## What to decide

- **Whether the package has a declared surface at all**, or is simply a tree of
  modules an application imports from directly. Both are legitimate; the second
  means the export check stays scoped to files permanently.
- **If it does: where the surface is declared.** An `index.ts` that re-exports,
  an `exports` map in `package.json`, or a convention plus a knip `entry` list
  are the usual three, and they differ in how much they constrain imports that
  exist today.
- **What happens to the six over-exported values.** Un-exporting them is the
  cheap answer and is a claim that nothing outside the package wants them.

## Acceptance

`knip` can be pointed at exports without producing findings that are not
defects, and a symbol exported for nobody fails CI the way an unimported module
already does.
