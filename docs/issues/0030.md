# 0030 — Let an expression say what one frame looks like from another

**Status:** Open
· **Kind:** RFC
· **Parent:** <a href="README.md" title="Issues">Issues</a>
· **Related:** <a href="0016.md" title="0016 — Make the document a program rather than a drawing">0016</a>,
<a href="0028.md" title="0028 — Decide how a signal is written in the editor">0028</a>

> A point on one frame, as some *other* frame sees it, is a thing rigs want
> constantly — and physm can express exactly one case of it: as the world sees
> it. `worldPoint` hard-codes the observer, and the world is not special enough
> to deserve that.

## What is true today

`worldPoint(frameId, local)` is the one signal leaf, and it answers in world
coordinates. `<WorldLine>` draws between two such points. Both name the world
because the pose map is keyed local→world and the root is where that walk ends.

But the pose of A as seen from B is just `M_B⁻¹ M_A`, and the world is the case
`B = root`. `Scene.getLocalPosition` is already the inverse of
`getWorldPosition` and has been all along, so the *machinery* for an arbitrary
observer exists; what is missing is a way to say it in an expression.

**The world is a default, not a kind.** Nothing about the root makes it a
different sort of thing from any other frame — except that it has no id, so
there is nothing to name it by. That is the only reason "world" reads as a
category rather than as an argument left out.

## The two questions

**What the expression looks like.** Something in the shape of
`pointIn(frame, local, observer)`, with `worldPoint(f, p)` its degenerate case.
Directions want the same treatment, and an orientation probably does too — a
crane arm's "which way am I pointing, as the cart sees it" is one expression,
not three special nodes.

**Whether the root becomes nameable.** The cheap answer is an optional observer
defaulting to the root, which keeps the world implicit and the special case
alive in the default. The honest answer is that the root gets a name and
`observer` is always given. The second is more work and is what actually
removes the privilege.

## Why this matters more than it looks

It is the difference between a capability and a pile of one-off nodes. Every
time a rig wants a relationship between two frames, the shape that has been
reached for so far is a new element with the reference baked in —
[`<WorldLine>`](0016/09-elements.md), and a `WorldSpring` that was written and
closed unmerged for exactly this reason. Each is cheap on its own and they do
not compose: two of them cannot be combined, named, or read in an expression.

A rest direction for a rotary spring is the case that prompted this, and it is
also the case that shows the split. "Hold the arm horizontal" relative to what
it is mounted on is a **local** rest and needs none of this — see `Spring.rest`.
Only a rest read against a *different* frame needs an observer, and when it
does, it wants the general expression rather than a spring-shaped exception.

## What it would take

**The leaf is the cheap half.** `Scene` can already answer it, and what it needs
first is [0028](0028.md) — how a signal is written at all — since an expression
naming two frames is two ids where that issue is already asking whether one
should be typed or picked.

**A spring consuming it is not**, and this is the part worth reading before
picking the issue up. A rest read against another frame makes the potential
depend on more than one coordinate. For a rotary spring wanting a fixed
orientation $`\alpha`$, the arm's absolute orientation is the sum of the
rotational coordinates above it, so

```math
U \;=\; \tfrac12 k\bigl(\theta_i - \alpha\bigr)^2,
\qquad
-\frac{\partial U}{\partial q^j} \;=\; -k\bigl(\theta_i - \alpha\bigr)
\;\text{ for every rotational } j \preceq i
```

— not for $`i`$ alone. The restoring torque enters several rows, and the force
vector stops being computable row by row, which is what
`get_force_vector_entry` and `JsSolver`'s per-row assembly do today.

That is the expensive half, and it is what sank the first attempt: a conservative
term written into one row when it belonged in several. It is recorded here
because the working plan that used to hold it has moved on, and because someone
reading only the paragraph above would size this as an expression-system job.

## What happens if this is not done

Every relationship between frames arrives as a new element with its reference
hard-coded, and the expression system ends up able to compute with numbers but
not with the scene's own geometry — which is the half of
[0016](0016.md) that makes the rest of it worth having.
