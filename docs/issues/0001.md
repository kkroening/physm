# 0001 — Give each constraint kind its own drift bound, and cover the behaviour changes the tfjs replacement left unasserted

**Status:** Open
· **Kind:** Enhancement
· **Parent:** <a href="README.md" title="Issues">Issues</a>
· **Related:** <a href="0002.md" title="0002 — Detect a scene that is fully pinned despite passing every structural check">0002</a>

> Replacing TensorFlow.js with a float64 matrix module ([#10](https://github.com/kkroening/physm/pull/10))
> turned over most of the `physm-js` suite, and left four loose ends behind it:
> a drift bound calibrated for one constraint kind but applied to both, a new
> `getSeparation` overload whose added branch no test executes, two production
> behaviour changes with no assertion, and a committed `.prettierrc` that
> nothing enforces.
>
> None of them is a hazard on a reachable path, and none is about float64 —
> which is why they were filed rather than folded into that PR. They are the
> residue of the change, and they are cheap.

## Background

`#10` ran to four review rounds, and the last two were finding problems in the
test suite rather than in the arithmetic. The change itself has been verified
since `0f33e17`; everything below is adjacent work that surfaced because the PR
happened to read that code closely.

## The drift bound is one literal for two kinds

`Constraint.test.ts`'s conservation test asserts a convergence *ratio* and a
*magnitude*, because neither implies the other: the ratio fails second order and
a stabilizer, while the magnitude fails an implementation that is faithfully
fourth order and drifting far too much. The magnitude is one shared literal, and
the two kinds' drifts differ by 18×:

| kind | `coarse` | slack vs `1e-5` |
| --- | --- | --- |
| `DistanceConstraint` | 4.650e-6 | 2.2× |
| `CoincidenceConstraint` | 2.594e-7 | 38.6× |

The bound was added to answer a review comment observing that the ratio had
*replaced* the old magnitude check rather than joining it — and the reply
claimed "the margin is a factor of three rather than the factor of 28 the old
bound carried". That lands for `DistanceConstraint`. For `CoincidenceConstraint`
the same literal is looser than the bound it was criticising.

Nothing is unguarded: the ratio assertion is tight on both branches and is doing
the real work. But the comment above the bound claims something it does not
deliver on one of the two branches.

### Proposal

Move the bound onto the kinds table beside `spacing`, so each kind carries its
own measured value where the geometry that produced it is visible:

```js
{ name: 'DistanceConstraint',    spacing: POLE_SPACING,           driftBound: 1e-5, … }
{ name: 'CoincidenceConstraint', spacing: POLE_SPACING - TIP_GAP, driftBound: 5e-7, … }
```

That also survives the next rig change better than a shared literal 250 lines
away — which is exactly how these two came apart, when the coincidence kind
gained its elbow.

## `getSeparation`'s two-id overload is unexecuted

`#10` gave `getSeparation` an overload pair so that `getSeparation('root', 'child')`
works and `getSeparation('root')` is a compile error. Every call site in the tree
still uses the four-argument form, so the branch the overload exists to add never
runs in the suite.

The compile-time half is the more valuable one to pin, and now that the suite
type-checks, a `@ts-expect-error` converts a one-off manual check into a standing
one — the build fails if the error ever stops being an error, which is the shape
of the bug the overload replaced:

```ts
expect(scene.getSeparation('root', 'child').distance).toBeCloseTo(
  scene.getSeparation('root', [0, 0], 'child', [0, 0]).distance,
);

// @ts-expect-error -- `frameId2` is required by the type, not by a runtime check
scene.getSeparation('root');
```

## Two behaviour changes are unasserted

- **`_getProjectedVelocities` re-wraps only `SingularMatrixError`** and rethrows
  everything else. Nothing asserts that a dimension error from `fromRows` reaches
  the caller unwrapped. This is the one worth writing if only one gets written:
  it is the place review found the change running *backwards* — re-diagnosing a
  structural bug as "rescale your scene" — so it has a demonstrated way of
  regressing. A scene whose `getMassMatrix` is stubbed one row short, asserting
  the dimension error rather than the conditioning text, covers it.
- **`DistanceConstraint.value` throws on an unresolved length** rather than
  computing `C` against zero. Nothing asserts it.

## The unused-variable check exempts almost everything

`eslint.config.js` sets `@typescript-eslint/no-unused-vars` to
`['warn', { varsIgnorePattern: '^[A-Z_]', ... }]`. That pattern was presumably
meant for unused React bindings under the classic JSX transform; under
`react-jsx` it mostly just exempts **every type and every class in the
codebase** from the unused check. `tsconfig.json` does not set
`noUnusedLocals` either, so nothing catches an unused import of a capitalised
name.

Found the hard way in [#14](https://github.com/kkroening/physm/pull/14):
deleting some tests left six dead imports that neither tool reported. A sweep at
that head found three more that predate it — `mat3` in `RotationalFrame.ts`,
`ZERO_STATE` in `Scene.ts`, and `React` in `App.test.tsx`, which `react-jsx`
makes unnecessary everywhere.

Worth deciding whether the pattern still earns its keep, and cleaning up what
turning it off reveals.

## Formatting drift

`prettier@3` against the committed `.prettierrc` wants to reflow six lines in
`Scene.tsx` — four added by `#10`, two older than it. There is no formatter in
`devDependencies`, and CI runs lint, typecheck, test and build but no format
check, so nothing catches this in either direction.

Either wire a format check into CI or drop the `.prettierrc`. A committed
convention that nothing enforces is the worst of the three states, because it
reads as a rule while behaving as a suggestion.
