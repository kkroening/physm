# 0016 — Make the document a program rather than a drawing

> A wish list arrived (_Karl, 2026-09-14_): parameterised composites, expressions
> with a real AST, repetition driven by a count, hand-written components mixed
> with visual ones, multiple child slots, springs, cross-frame references,
> outputs, algebraic enums, manipulator handles, external forces, key bindings.
> Eleven features, and they are one feature.

**The verdict up front: the simulation core is fine and barely touched; the
editor's document model needs one layer it never had; and the addressing scheme
underneath it should change once, early, because that is the only genuinely
invasive part.**

**Every item on the list is the same shift.** The document today is a *drawing of
one scene*. Each wish asks it to become *a program that produces scenes*:
parameters are arguments, expressions are computation, repetition is iteration,
outputs are return values, slots are multiple argument groups, manipulators and
force channels are an I/O surface, enums are sum-typed arguments, and
hand-written components are subprograms in the host language. That is not a
coincidence to be admired — it is the thing to design once instead of eleven
times.

**And physm already has a program representation: the TSX it emits.**
`buildScene` already calls composites and assembles what they return. The
document model is a *restricted subset* of that, which gave up programmability in
exchange for being directly editable. So most of this work is closing the gap
between the document and its own output format, not inventing a new machine.

That gives the rule this whole RFC hangs on, and a principled way to settle every
future argument about whether a feature belongs in the document:

- **The document is a decidable subset of TSX that round-trips.**
- **Hand-written components are the escape hatch for everything outside it.**
- **The subset grows deliberately** — parameters, then expressions, then slots,
  then repetition — and the emitter is both the specification and the test. A
  feature that cannot round-trip through `emitScene` and back is not designed
  yet.

**The one distinction to fix before anything else** is between values that are
**structural** — evaluable at build time from parameters and constants, deciding
the scene's shape — and values that are **signals**, evaluated per tick against a
pose. It is not academic: it is what makes a repetition count tractable, what
makes a line drawn between two moving anchors possible at all, and what answers
the reasonable worry that outputs are the React mistake of asking an element for
its rendered position. [Page 2](0016/02-values.md).

## What this settles elsewhere

Three of the tracker's open RFCs are downstream of this rather than merely
adjacent, and the accounting is worth stating rather than implying:

- **[0011](0011.md)** — the demo reaches a frame from outside the scene by id, so
  "the frames are generated, not named" is broken exactly once and the app holds
  the string. A declared port surface is what a scene should expose instead, and
  external forces and key bindings are the same need arriving from the other
  direction. [Page 3](0016/03-scope.md).
- **[0003](0003.md)** — `Decal.xform(m)` returns a decal in transformed
  coordinates and has no caller outside the test suite. A decal drawn in world
  space between two moving points is precisely that caller, which turns the
  question from "which of these two is the API" into one with an answer.
  [Page 9](0016/09-elements.md).
- **[0005](0005.md)** — sibling order is first-registration order, which is JSX
  order only for a tree whose shape never changes. Repetition makes the shape
  change by construction, so this stops being a latent correctness question and
  becomes a blocking one. [Page 6](0016/06-structure.md).
