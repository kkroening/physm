# 0011 — Give the binding a way to name a frame from outside the scene

**Status:** Open
· **Kind:** RFC
· **Parent:** <a href="README.md" title="Issues">Issues</a>
· **Related:** <a href="0006.md" title="0006 — Let a JSX rig be assembled without mounting a renderer">0006</a>

> `<Anchor>` solves "name a generated frame" *for constraints* — it wires one
> part of a scene to another. There is no equivalent for reaching a frame from
> **outside** the scene, and the demo needs one: the controls push the cart by
> id.
>
> So the rig has to break its own "the frames are generated, not named" story
> exactly once, and the app has to hold the string it broke it with.

## Background

Raised during review of [#22](https://github.com/kkroening/physm/pull/22), the
binding's first real consumer — and the gap turned up immediately, in the one
interaction the demo actually has.

`CartAndRope.tsx` names its cart `CART_FRAME_ID` and exports it; `App.jsx`
imports it to key an external force map. Every other frame in the rig is
generated and named by its component key, which is the point.

That is not wrong — a written id at the app boundary is defensible — but it is
unexamined, and a second consumer will hit the same place. Anything reading a
coordinate back out (a readout, a chase camera, a test that pokes one joint)
needs the same handle.

## The options

- **Written ids are correct at the boundary.** Generated ids are for the
  interior, where nothing outside needs to name them; anything the app touches
  gets a name on purpose. Cheapest, and arguably says something true — the cart
  *is* part of this demo's public shape. Then the thing to add is a sentence
  saying so, not code.
- **An `<Anchor>` whose ref a parent reads.** The mechanism already exists and
  already reports a `frameId`; today only constraints consume it. A rig could
  hand its cart out the same way it hands out a rope tip, and the app would hold
  a ref instead of a string.
- **A `sceneRef` beside `onSceneChange`.** Gives the app the assembled scene and
  lets it find frames however it likes. Most flexible, least guided, and it
  makes every frame's generated id part of the surface by accident.

## Acceptance

A decision, recorded. If it is "written ids at the boundary", that belongs in
`physm-js/README.md` beside the authoring example, since it is a rule an author
needs and cannot infer.
