# 0012 — Give `physm-rs` its own stabilizer, so `RsSolver` need not step one at a time

**Status:** Resolved
· **Kind:** Enhancement
· **Parent:** <a href="README.md" title="Issues">Issues</a>

> Projection stabilization is implemented in TypeScript. `RsSolver` reaches it
> by giving up its batched wasm path and stepping one tick at a time, correcting
> from the JavaScript side after each one. That works and is correct; it is also
> measurably slower than the path it replaces, and the slowdown is pure boundary
> crossing rather than physics.

## Background

`Scene.getStabilizedState` pulls the state back onto the constraint manifold
after a step — the projection row of the strategy table in
[`constraints.md` §7](../constraints.md#7-drift-and-how-it-gets-fixed). The hook
that applies it lives on `Solver`, above both integrators, because correcting
needs only `getStateMap` and `setStateMap`. That placement is deliberate and
worth keeping: the JavaScript and Rust paths get the same correction from the
same code, rather than two implementations that could disagree.

The cost falls on `RsSolver`. Unstabilized it hands `tickCount` straight to wasm
and integrates the whole batch without crossing back. Stabilized it must call
wasm once per step, because correcting once per batch would be a different
amount of stabilization for the same physics depending on what a caller passed.
Measured on the demo rig, 10 000 steps: 347 ms unstabilized, 726 ms stabilized.

Some of that is the stabilizer's own two solves, which any implementation pays.
The rest is the boundary, and only a Rust-side implementation removes it.

## Proposal

Implement the same projection in `physm-rs`, called from inside the tick loop,
and let `RsSolver` keep passing `tickCount` through.

The blocker is the fourth seam in
[`constraints.md` §7](../constraints.md#7-drift-and-how-it-gets-fixed): the
kinematic sweeps have to be callable as a function of $q$ alone, because Newton
evaluates `value` and `jacobian_rows` at trial configurations no solve was run
at. `physm-js` has that as `Scene.getConfigKinematics`; in `physm-rs` the sweeps
are private free functions reachable only through `get_system_of_equations`,
which also builds everything projection does not want. Extracting them is the
bulk of the work.

Two things to decide rather than assume:

- **Whether the flag stays one flag.** Today `stabilize` is a `Solver` option
  meaning "correct after each step". If Rust gains its own, the flag has to keep
  meaning one thing across both solvers, or the cross-validation tests stop
  comparing like with like.
- **Whether the TypeScript path stays.** `JsSolver` still needs it, so the
  answer is probably yes — which means the two implementations have to be held
  to the same result by test, not by intention.

## Resolution

`physm-rs` carries its own projection — `stabilize_mut`, called at the end of
`tick_mut` — and `RsSolver` hands `tickCount` straight to wasm again. On the demo
rig, 10 000 steps: 402 ms stabilized against 726 ms correcting from TypeScript,
and 359 ms unstabilized. Stabilization costs about 1.12× rather than 2.1×, though the two unstabilized
figures time the same path and differ by 3.5%, which is more spread than the
ratio is being quoted to.

**The stated blocker had already been removed.** This issue said `physm-rs`'s
kinematic sweeps were reachable only through `get_system_of_equations` and would
need extracting. They were extracted when the constraint work landed —
`get_config_kinematics` was already there, with `ConstraintCtx`'s velocity fields
made optional for exactly this purpose. Seam 4 held; the issue was written from a
stale reading of it.

**Both open questions resolved the way the issue guessed.** The flag stays one
flag meaning one thing, now plumbed through `setStabilize` on the wasm boundary
and defaulting on in both implementations. The TypeScript path stays, because
`JsSolver` needs it.

**And the "held to the same result by test, not by intention" note earned itself
immediately.** The cross-validation added for it found a real divergence on its
first run: `physm-js`'s velocity half skips its solve when `J q̇` is already
within tolerance, relative to how much cancellation produced the residual, and
the first Rust version corrected unconditionally. Measured, the two drifted apart
by `3.7e-8` after two seconds and `5.4e-5` after ten, against `7.1e-15` and
`9.5e-12` for the same pair unstabilized. With the early-out ported they agree to
`4.6e-12`, the same order as the unstabilized pair.

Nothing else would have caught it. It is not a crash, not a test failure, and not
visible in either implementation read on its own.

## Acceptance

`RsSolver` stabilizes without reducing its batch size, and a cross-validation
test pins the Rust and TypeScript corrections to the same trajectory on a rig
driven hard enough to drift.
