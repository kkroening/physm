# 12 — The wish list, verbatim

The message this RFC replies to, reproduced unedited (_Karl, 2026-09-14_). The
eleven pages before this one quote it, agree with parts of it, and argue against
others; this page is here so that every one of those can be checked against the
source rather than against the RFC's own summary of it.

Two things about it are worth saying before reading. It was written as an
opening move — "just getting the ball rolling" — rather than as a specification,
so its tentative parts are tentative on purpose. And it is the *only* statement
of what the overhaul is for: the issue is the permanent record, and a message is
not.

---

Discussion-only for a moment: It's time for the next major overhaul / round of improvements.

For starters, here are some of the things on the wish list:

* Composite components should optionally be able to have custom input props that can be referenced in various child props. For example, Pendulum could have a `length` prop, `PendulumCart` could have a `pendulumCount` + `pendulumLength` (and other props) and it would instantiate the children accordingly.
* It should be possible to use expressions for props - and not just in an `eval` / code injection manner, but rather in a way that physm understands the overall AST-like structure / graph relationship of the corresponding expressions.
* Ideally, the expressions would have another visual editor pane that lets you see the graph representation of the AST, and you can connect AST nodes either visually, or by typing the expression in the prop editor, or ideally in the future by editing the code (although that last part gets quite a bit more difficult, so it's a longterm vision to strive towards).
   * The AST graph editor would be like Unreal Engine's shader graph and/or blueprint system.
   * Even without the visual AST graph editor, I'm guessing the expression system is probably reasonably within reach in the near term. The `pendulumCount` example might be especially tricky though - I'm not sure how the user would express that a node should be repeatedly nested - i.e. some way of saying "Create a Pendulum node in the RotationalFrame, but within the Pendulum, create another Pendulum, and within that create another Pendulum, with the number of such nestings dependent on the input `pendulumCount` prop. This would be its own feature. One way I imagine it working is having a special node type that takes a child/children, and then re-instantiates it multiple times and stacks it; i.e. whatever children you put in it get instantiated N times or whatever. The tree view would just have the `NestedForLoop` (needs a better name) with a `Pendulum` as its children, and then when the composite component is actually instantiated, the `NestedForLoop` gets rendered out to just the nested `Pendulum`s or whatever. I don't want to get too fixated on this particular problem right now since it's more of a nice-to-have but maybe helps to think about in shaping the expression system implementation, to leave room for it.
* It should be possible to mix and match visually authored components with hand-written components. It's already sorta possible in the sense that you can hand-write JSX/TSX code ahead of time in the physm repo source, but I'm talking about being able to hand-write TSX directly in the Physm editor UI. When you drill into the detail for a composite component, you could switch it to become a hand-written component, where the code editor becomes mutable, and the tree view becomes read-only (i.e. opposite of how the visually authored components are done). There might be either an explicit disclaimer (e.g. one-time warning, and/or exclamation icon that if you mouse over it gives the explanation) that switching back to visual/interactively authored component does not preserve the source code / comments / etc. and instead simply captures the result of calling the component function which produces a particular component tree. You could mix and match such composite components, where e.g. the scene is visual, a PendulumCart is hand-written (which also happens to be a potential way to solve the `pendulumCount` problem in the relativily near term without the `NestedForLoop` or whatever), and it contains `Pendulum` which is visual.
   * Note that this is substantially simpler than the full-blown bidirectional code-vs-tree editing, because we still have a single source of truth in this case rather than bidirectional. But we'll still need to do runtime compilation of JSX/TSX like with those JS code playground apps or whatever.
* It turns out that there's probably no fundamental reason that composite components should have to accept only one slot for nested children to be mounted. For example, a `DualAntennaCart` might have two poles sticking out of it - one pointing to the left, and the other to the right, both being able to rotate/swivel but each with a built in rotary spring that tries to keep the pole horizontal like a crane - and it should be possible to mount separate children to the left pole vs right pole. The `DualAntennaCart` component would have two separate child slots, and then when it's instantiated in the scene (or another composite component) there would be a way of attaching the two sets of children and somehow indicating which slot each set of children is going into - e.g. by numerical position or by named slot, etc. I imagine this isn't unlike typical React app development, where you might have e.g. a view layout component that accepts multiple sets of children. On the definition side perhaps it's a matter of allowing multiple `Children` nodes to be defined and giving them an optional slot name, but I'm not sure how the instantiation side would work - TBD.
* Springs - both linear and rotary: Fairly self-explanatory - linear springs have start and end positions; rotary springs are a little trickier, but imagine the AntennaCart arm for example, where the arm can rotate but has a restoring force that gets stronger at greater angles.
* Directional references: Like in CAD / Fusion where you can have a node reference some axes defined elsewhere in the scene, it would be useful to be able to have an expression reference a point, direction, etc. from another frame. Perhaps the other frame contains a node that places a direction arrow in the frame that you can click/drag and reorient; and then in the dependent frame you'd create a node that pulls the external vector into this frame's scope as a sort of imported symbol that you'd give a name in the local scope, which can then be referenced in expressions within the component's scope.
   * It's tempting to say that the vector in the other frame would just get a globally unique name that the dependent component could reference verbatim, but it feels like playing with fire, just like relying on globals in general. Actually, this suggests that the vector should really be an input prop.
   * Props should probably appear as nodes in the tree view, just that the prop nodes should only be at the top level of the tree, before any nested components; prop nodes would have a type like String, Position, Direction, TangentVector; exact names are TBD; but one should be aware that a point with direction is a distinct thing from just a point or just a direction; or maybe such a thing should just be two separate props - TBD.
   * It also suggests that composite components should be able to have "outputs" (if that's the right word) in addition to just the nodes that effectively come out of the `return (<> ... )` of the component function. For example, in a Pendulum, you might export/output a point at the position of the bob, and then a caller component that instantiates a Pendulum could reference the pendulum's named output to use it in expressions. Like maybe when you instantiate the Pendulum you can optionally give it a locally scoped name, like `leftPendulum`, and then reference elsewhere in the component like `leftPendulum.bobPosition`. This seems appealing; but I do wonder if this is similar to the predicament in React where one is tempted to be able to interrogate a fragment/element to ask for its physically rendered position in the actual DOM - e.g. pixel coordinates, which AFAIK is impossible and perhaps even ill-advised at a conceptual level for whatever reason; I'm triyng to imagine the analogy here because physm components are only partially correlated to (V)DOM elements or even React elements in the sense that the Physm JSX/TSX scene representation rightfully doesn't try to animate via React re-rendering but uses it as a structural representation; frame-relative positions are somewhat static but when it depends on the current state which changes from one tick to the next it gets tricky. It would be super powerful and perhaps even necessary to some degree to have a way of using child-derived outputs in enclosing scopes' expressions; for example, suppose you have a Distance constraint and you wish to draw a Line between the two anchors; the end position is based on the anchor positions in different frames, so if you could use e.g. `RopeCart.bobPosition` as the line's end point and `Crane.armEndPosition` , or by assigning a `distConstraint` name to the Distance constraint node so that it appears as a local variable so that you can use  `distanceConstraint.endPosition` in an expression, the solution becomes intuitively obvious, in the code, in the tree view, and in the expressions in the prop editor, and eventually also the AST expression graph view.
* Algebraic enums: There are plenty of conceivable cases where you could either pass one set of props or another; for example, Line could take either start position + end position, or start position + angle + distance. I imagine having Rust-like enums that encapsulate such either-or, mutually exclusive prop groups/structures. The alternative is having either different node types entirely, like AngleLine vs ConnectingLine (yuck, and a combinatorial nightmare), or convoluted nullable props with intricate rules (like endPos must not be specified if angle is specified, or whatever). This is definitely in the nice-to-have category, but something to think about.
* Manipulator handles: I imagine being able to create manipulator handle nodes in components to make them easily customizable in the caller's scope. For example, DualAntennaCart could have a manipulator for each antenna that lets the caller click and drag to change the antenna length + initial angle; and/or another horizontal-only resizing manipulator that lets the cart be stretched/shrunk horizontally. Unless there's a way for the author of DualAntennaCart to place such manipulator nodes, we can't just blindly guess what manipulators ought to be available since there could be a lot of smaller nested components that don't make sense to modify in the calling scope. The manipulators would be nodes that can have local variable names and used in expressions.
* External forces: Similar to manipulator handles, there could be a way to place nodes that allow the component to receive external forces. Like a BallAndChain component, the ball could receive external forces so that at gameplay time, the user can click and drag the ball to interact with it - i.e. providing external forces in the global X/Y directions, rather than directly forcing a frame's degree of freedom - e.g. a Cart's TrackFrame's position, or a Pendulum's RotationalFrame angle - though that would be useful too, like being able to inject an external rotational force on a particular RotationalFrame.
* Keyboard inputs: I'm not sure exactly how, but there should be a way to indicate that certain keys lead to certain external forces or other interactions - like left/right arrows moving the cart left/right.
   * Ideally also a way to have more elaborate expressions for the forces; for example, if you make the cart take a constant left/right force value that doesn't depend on how fast the cart is already moving or how much load the cart is encountering, it can be either sluggish or too forceful, whereas a more elaborate expression that uses a greater force when the cart is moving slowly and capping out if the cart is moving fast, it can make the game/simulation feel much more responsive. There should be a way to define (typically at the scene level) that a certain key should produce an external force, "routed" via expression(s) that consider other factors like current cart position, and delivering the force to a corresponding external force node; like perhaps DualAntennaCart has a force node for the cart position so that the caller can refer to it via `cart.trackForce` and then create a node at the scene level that binds the key with an expression to delivering the force.


Anyways, just getting the ball rolling on this for now and capturing the ideas. I'm really curious to hear your thoughts, and whether you think this stuff is doable. I wonder if Physm is gonna need substantial redesign to make this possible, since we haven't had a chance to take a step back and clean up the code and make the architecture able to scale to this substantial jump in sophistication.
