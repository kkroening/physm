# 0022 — Decide whether the parameter types grow toward the prop kinds

**Status:** Open
· **Kind:** RFC
· **Parent:** <a href="README.md" title="Issues">Issues</a>
· **Related:** <a href="0016.md" title="0016 — Make the document a program rather than a drawing">0016</a>

> Promoting a prop into a parameter **widens its contract**, because the
> parameter type set is coarser than the prop-kind set. A `length` becomes a
> `scalar` and stops being non-negative; a `color` and a constraint's `end`
> both become a `label` and stop being a colour and an id. Nothing says so —
> the mapping reads as a table of equivalents. Either the type set grows toward
> the kinds, or promotion is deliberately lossy and says as much where a person
> can see it.

## What is true today

`PROMOTED_TYPES` maps seven of the nine prop kinds to a parameter type and
refuses the other two:

| prop kind | parameter type | what is lost |
| - | - | - |
| `number` | `scalar` | nothing |
| `angle` | `angle` | nothing |
| `point` | `point` | nothing |
| `length` | `scalar` | non-negative |
| `color` | `label` | is a CSS colour |
| `end` | `label` | resolves to a frame or an anchor; **and its candidate list** |
| `name` | `label` | nothing much — an id is a string |
| `flag` | — | refused: there is no boolean type |
| `state` | — | refused: a coordinate *and* its rate |

So the rule is not "refuse rather than approximate", which is what the code's
own comment used to imply. It is **approximate where the approximation can hold
the value, refuse where it cannot** — a threshold, applied silently.

**The candidate list is the sharpest loss**, because it is visible rather than
theoretical. `PropField` gives only kind `end` a datalist of the scene's ids. A
promoted `frame1` is a `label` parameter, a `label` is edited as kind `name`,
and kind `name` has no datalist — so an instance passing that end types a bare
string with nothing to complete against. Mapping `label` to `end` instead would
hand a promoted *colour* an id-completion field, so the widget cannot be fixed
without fixing the types.

## The two answers

**Grow the set.** `Length`, `Color` and `End` (or `Id`) become parameter types
of their own, with the widgets and the validation that implies.
[0016 page 3](0016/03-scope.md) already anticipates `Direction` and `Frame`
arriving, so the set is expected to grow — this is a question of *which way*,
not whether.

- A definition's declared surface then says as much as a building block's does,
  which is the property the port surface is for.
- It is more types to carry through `PARAMETER_TYPES` (the emitter),
  `PARAMETER_KINDS` (the pane), `fitsType`, and whatever expressions add.

**Keep it lossy, and say so.** The set stays at what
[0016 page 3](0016/03-scope.md) names, and promotion's button says what the
prop will stop guaranteeing.

- Fewer types, and a parameter stays a thing an *instance* supplies rather than
  a re-statement of the component's own contract.
- A person promoting a width can then be passed a negative one, and finds out
  when the scene refuses to build.

## Why it is worth deciding before expressions

[0016](0016.md)'s next step has a prop hold `mul(halfLength, 2)`, and that asks
the same question from the other side: is the result of an expression on a
`length` prop still non-negative, and what checks it? Whatever answers that for
expressions should answer it for parameters, because they are the same
question about the same props — and answering it twice would mean two rules
about what a prop's declared kind guarantees.

## What happens if this is not done

Promotion goes on widening contracts quietly. The failure is not loud: a
negative width or a non-colour colour reaches the component, which either
refuses to build or draws something odd, and the person traces it back to a
promotion they made earlier with nothing on screen having warned them.
