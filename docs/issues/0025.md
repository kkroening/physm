# 0025 — Decide whether the expression language has exponentiation

**Status:** Open
· **Kind:** RFC
· **Parent:** <a href="README.md" title="Issues">Issues</a>
· **Related:** <a href="0022.md" title="0022 — Decide whether the parameter types grow toward the prop kinds">0022</a>,
<a href="0024.md" title="0024 — Say what unit an angle typed as an expression is in">0024</a>

> [0016's expressions design](0016/04-expressions.md) offers
> `sqrt(x**2 + y**2)` as an example of what a person types into a prop box. The
> parser refuses it, because there is no `**` token — and there is no `pow`
> among the operations either, so the nearest thing that works is
> `sqrt(mul(x, x) + mul(y, y))`: infix and constructor form mixed, in a feature
> whose premise is that a person would not have to mix them.

## What is true today

Eleven operations, none of them exponentiation. The grammar has `+ - * /`,
unary minus, parentheses and calls. `x**2` refuses at the first `*` it cannot
pair.

So the design's own example does not work, and the workaround asks a person to
know both forms and switch between them mid-expression.

## The two shapes of answer

**`pow(x, 2)` as a twelfth operation.** Cheap: one line in the operations
table, and the parser accepts it the moment it exists, because a call to any
operation already parses. Nothing else moves.

- It leaves `x**2` refused, so the design's example still does not work as
  written and the quote wants trimming instead.
- Squaring reads as a function call in a language that has infix for the other
  four, which is the mixing this was meant to avoid — just less of it.

**`**` as a token as well.** Right-associative, binding tighter than unary
minus, so `-x**2` is `-(x²)` as it is everywhere else.

- The design's example works as printed.
- It is the first operator whose *printed* form is not a call, unless
  `expressionSource` learns to print it too — and if it does, the printer stops
  being uniformly constructor-form, which is the property that made the
  emitted module's shape simple to reason about.

## The syntax is not the question

**`**` was an example rather than a requirement, and whatever spelling is best
is the implementer's call** _(Karl, 2026-09-16)_. So what is left of this issue
is the smaller and harder half: whether the language should have exponentiation
at all.

That also removes what looked like the binding constraint. `**` seemed forced
by JavaScript, and it is not: what a document *stores* is a call, and what the
emitter *prints* is a call, because hand-written TSX cannot spell exponentiation
infix either — there is no operator overloading to spell it with. So the only
thing under discussion is the surface a person types into a prop box, which is
free to be whatever reads best there.

`^` is the obvious candidate on those terms: it is what a calculator and a
spreadsheet take, and the reason to have flinched from it — that it means
exclusive-or in JavaScript — turns out not to reach the prop box, where no
JavaScript is being written. It is a lean rather than a decision; nothing here
is settled until the question above it is.

## Why it belongs with 0022 and 0024

All three ask what the language admits, and each is cheap alone and awkward
three times:

- [0022](0022.md) — do the parameter types grow toward the prop kinds?
- [0024](0024.md) — what unit is an angle expression in?
- this one — what arithmetic is there?

An answer to any of them constrains the others: a `Length` type wants to know
whether squaring can produce one, and an `Angle` that carries a unit wants to
know what raising it to a power means. Those are unaffected by the syntax half
being settled above — they are about what the operation *means*, which is the
half still open.

## What happens if this is not done

A person who reads the design and types its example is refused, and the
workaround is uglier than the thing the feature was for. Nothing breaks.
