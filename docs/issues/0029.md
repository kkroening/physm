# 0029 — Derive whether a mounted tree has any content, rather than enumerating it

**Status:** Open
· **Kind:** Enhancement
· **Parent:** <a href="README.md" title="Issues">Issues</a>
· **Related:** <a href="0016.md" title="0016 — Make the document a program rather than a drawing">0016</a>

> `<Scene>` decides whether there is anything to assemble by listing every kind
> of content it knows about. The list has gone stale twice in two changes, each
> time letting the mounted route answer "there is no scene" where `buildScene`
> answered something — which is the one disagreement between the two routes the
> whole differential suite exists to rule out.

## What is true today

`Scene.tsx` guards assembly with a conjunction over `root.frames`,
`root.decals`, `root.weights`, `root.springs` and the world decals. An empty
registry has to answer `null` rather than assemble, because the tree registers
one effect at a time and an empty one is an ordinary intermediate state.

The guard is an enumeration, and every new kind of content has to be added to
it. Twice now that has been noticed only by a test:

- **World-space decals.** `buildChildren` puts nothing in `root` for one, so a
  tree whose whole content was `<WorldLine>`s read as an empty tree while
  `buildScene` built it.
- **Springs.** These *do* land in `root.springs`, and the guard did not look at
  the field — so a tree of only a root `<Spring>` answered `null` in one route
  and threw the refusal in the other.

`buildScene` has no such guard at all, which is why the disagreement is always
in this direction.

## What it would take

Ask whether anything **registered**, rather than what kind of thing it was:

```js
const live = [...registry.entries.values()].filter((entry) => entry.live);
if (!live.length) { … }
```

`live` is already computed one line above, so the guard gets shorter as well as
harder to leave stale.

## Why it is filed rather than done

It is not behaviour-preserving, and the change that found it was a migration
that should change shape and nothing else.

Two degenerate trees answer differently afterwards: one holding only an
`<Anchor>`, and one holding only a constraint. Today both read as no scene at
all; derived, both would assemble — the anchor contributing nothing, and the
constraint reporting that it names frames the scene does not have.

That is arguably the better answer in both cases, and it is a judgement about
what `onSceneChange` should fire with rather than a bug fix. It wants deciding
on its own.

## What happens if this is not done

The next kind of content added to a frame or a scene has an even chance of
repeating it, and the symptom is the quietest one this codebase has: a scene
that simply does not appear, in one of the two routes, with nothing thrown.
