# 0029 — Derive whether a mounted tree has any content, rather than enumerating it

**Status:** Open
· **Kind:** Enhancement
· **Parent:** <a href="README.md" title="Issues">Issues</a>
· **Related:** <a href="0016.md" title="0016 — Make the document a program rather than a drawing">0016</a>

> `<Scene>` decides whether there is anything to assemble from what landed in
> the frame tree. It now reads that generically, so it cannot go stale as the
> tree grows — but it still ignores the two node kinds that belong to the scene
> rather than to a frame. Whether *those* should count is a question about what
> `onSceneChange` fires with, not a defect.

## What is true today

`Scene.tsx` guards assembly by asking whether *every* collection `buildChildren`
produced is empty, plus the world decals. An empty registry has to answer `null`
rather than assemble, because the tree registers one effect at a time and an
empty one is an ordinary intermediate state.

**The staleness this was filed for is fixed.** The guard used to name each
collection, and that list went stale three times in three changes — world-space
decals, then springs, then world springs — each time letting the mounted route
answer "no scene" where `buildScene` answered something, which is the quietest
failure this binding has. Reading `FrameChildren` generically means a new
collection counts by existing.

What is left is narrower and is a design question rather than a defect: the
guard still does not count the node kinds that belong to the **scene** rather
than to a frame. World decals are counted by hand; constraints and anchors are
not counted at all.

## What it would take

Ask whether anything **registered**, rather than what landed in the frame tree:

```js
const live = [...registry.entries.values()].filter((entry) => entry.live);
if (!live.length) { … }
```

`live` is already computed a few lines above, so the guard gets shorter as well
as wider, and the hand-written world-decal clause goes with it.

## Why it is still open

It is not behaviour-preserving. Two degenerate trees answer differently
afterwards: one holding only an `<Anchor>`, and one holding only a constraint.
Today both read as no scene at all; derived, both would assemble — the anchor
contributing nothing, and the constraint reporting that it names frames the
scene does not have.

That is arguably the better answer in both cases, and it is a judgement about
what `onSceneChange` should fire with rather than a bug fix.

## What happens if this is not done

Less than when it was filed. The recurring defect is closed; what remains is
that a scene-level node kind still has to be remembered here — which is one
hand-written clause today, and would be two if constraints or anchors ever
needed to count.
