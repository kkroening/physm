# 0005 — Give JSX siblings their tree order, which effect registration cannot

**Status:** Open
· **Kind:** RFC
· **Parent:** <a href="README.md" title="Issues">Issues</a>
· **Related:** <a href="0006.md" title="0006 — Let a JSX rig be assembled without mounting a renderer">0006</a>

> Sibling order in an authored scene is *first-registration* order. For a tree
> whose shape never changes that is JSX order, because React runs sibling
> effects left to right. For a sibling that mounts later — one behind a
> condition that flips — it is not: the newcomer appends rather than taking the
> position it occupies in the JSX.
>
> Sibling order is not cosmetic. For decals it is SVG paint order; for frames it
> is the order of `sortedFrames`, which indexes the mass matrix and the
> Jacobian's columns.

## Background

From review of [#15](https://github.com/kkroening/physm/pull/15), which added
the JSX authoring components.

A related bug — a *prop change* reordering a node behind its siblings, because
`Map.set` after `delete` re-inserts at the end — was fixed in that PR by
flagging unmounted entries instead of deleting them, so a re-registering node
keeps its slot. That covers every case where the tree's shape is stable.

What it cannot cover is a node that was never registered before. There is
nowhere to put it except the end, because nothing in the registry knows where
its JSX position is.

## Why the obvious fixes do not work

**Sorting by `useId`.** React allocates ids in render order, which is tree
order, so this looks promising. It is base-36 — `_r_0_` … `_r_9_`, `_r_a_` — so
lexicographic comparison breaks at the 37th component, where `_r_10_` sorts
before `_r_9_`. It is also an undocumented internal format.

**Indexing children with `React.Children`.** A parent can number its own JSX
children, but a *composed* component breaks the correspondence: a `RopeChain` in
the middle of a frame's children is one JSX child and contributes several
frames. Numbering by JSX position would give all of them one index. Every
intervening component would have to participate in the scheme, including
user-written ones, which is not a thing a binding can require.

**Registering during render instead of in an effect.** Render order *is* tree
order, but a render may be discarded or replayed, so a registry written during
render would accumulate nodes that never mounted.

## The real answer, and the cheap one

**A custom reconciler** is the mechanism that has this information: it is
handed the tree and its order directly, rather than inferring order from the
sequence effects happen to fire in. That was always the intended endpoint —
effect-based registration was chosen as the first step, not the destination —
and sibling ordering is the first concrete thing that needs it.

**In the meantime**, the choice is between:

1. **Documenting it**, which is what [#15](https://github.com/kkroening/physm/pull/15)
   does: `useSceneNode`'s docstring states that a later-mounting sibling
   appends. Honest, and wrong for anyone who hits it.
2. **An explicit `order` prop** on the components, so an author who cares can
   say. Cheap, ugly, and it puts a React implementation detail in the scene
   language.

## Acceptance

Either a reconciler that gets order from the tree, or a decision that sibling
order among conditionally-mounted nodes is unspecified — written down where an
author reads it, not only where an implementer does.
