# 0019 — Decide whether physm owns its element type, or keeps borrowing React's

**Status:** Open
· **Kind:** RFC
· **Parent:** <a href="README.md" title="Issues">Issues</a>
· **Related:** <a href="0016.md" title="0016 — Make the document a program rather than a drawing">0016</a>,
<a href="0005.md" title="0005 — Give JSX siblings their tree order, which effect registration cannot">0005</a>,
<a href="0017.md" title="0017 — Give the document a save format, since its own output cannot carry it">0017</a>

> `<RotationalFrame />` compiles to `React.createElement`, so a scene tree is a
> tree of **React elements** that physm then interprets. Several open problems
> turn out to be consequences of that borrowing rather than difficulties of
> their own — `emitScene` meeting a `$$typeof` symbol, a component that cannot
> cross a worker boundary, hooks being a dilemma, and
> [0005](0005.md) existing at all. A JSX factory of physm's own would make
> `<Multiply a={x} b={y}/>` produce a physm node instead. That is a large
> change and it should be decided before [0016](0016.md)'s expression system is
> built on the answer.

## What is true today

**A core component is two things bolted together**, and the seam is visible in
the source. `RotationalFrame` is a React function component whose body registers
into a context-provided registry:

```tsx
export default function RotationalFrame(props: RotationalFrameProps): ReactElement {
  const key = useId();
  const frameId = useContext(FrameIdContext);
  const node = describeRotationalFrame(props, { key, frameId });

  useSceneNode(key, node, { ...props, frameId });

  return (
    <ParentKeyContext.Provider value={key}>
      <FrameIdContext.Provider value={node.id}>{children}</FrameIdContext.Provider>
    </ParentKeyContext.Provider>
  );
}

RotationalFrame.sceneNode = describeRotationalFrame;
RotationalFrame.meta = { /* … */ };
```

The function body serves the **mounted** route. The `sceneNode` static serves
the **walk**: `buildScene` reads `type.sceneNode` and calls *that*, never the
component. So the walk already treats a core component as data — it calls only
*composites* as functions.

Two routes, then, over one set of components:

| route | who uses it | how a node is produced |
|---|---|---|
| mounted — `<Scene>` + `useSceneNode` | the demo (`App.jsx`) | React renders; effects register; the registry assembles |
| walk — `buildScene` | the editor | the tree is read; `type.sceneNode` is called directly |

`tsconfig.json` sets `"jsx": "react-jsx"`, so every tag goes through React's
automatic runtime. That is the single line this RFC is about.

## What the borrowing costs

Four open problems, each of which reads as its own difficulty and is a
consequence of the element being React's.

- **`emitScene` cannot write an element-valued prop.** Its `literal()` walks a
  plain object and meets React's `$$typeof` **symbol**, which is not
  expressible as source. Named slots ([0016 page 6](0016/06-structure.md)) need
  exactly that, so the emitter needs widening for a field React put there.
- **A hand-written component cannot be called in a worker.** Its return value is
  an element tree whose `type` fields are *function references*, and structured
  clone refuses a function — so the hang [0016 page 11](0016/11-risks.md)
  records as open lands on the main thread. A node naming its component through
  a registry key is plain data and crosses freely.
- **Hooks are a dilemma only because of the walk.** The repo deliberately keeps
  components hook-free so `buildScene` can call composites outside React, with
  a test that walks every composite outside a render. Wrapping React rather than
  exposing it — physm's own `useState`, dispatching on context — is the answer
  Karl reached independently, and it is only available if the node is ours.
- **[0005](0005.md) exists because mounting orders siblings by registration.**
  `buildScene`'s docstring already says the walk has no such problem. If the
  walk were the only route, 0005 would not be fixed — it would **stop
  existing**.

## What owning it would look like

`jsxImportSource` pointing at a physm runtime, so a tag produces:

```ts
interface PhysmNode {
  readonly type: string;        // a registry key, not a function
  readonly props: DocProps;
  readonly key?: string;
  readonly children: readonly PhysmNode[];
}
```

Plain data, serializable, with no symbols and no function references. Which is
the same shape as [0016](0016.md)'s expression nodes — `mul(a, b)` returning
`{ kind: 'mul', a, b }` is this idea already, applied to expressions. Owning the
element type is the same move applied to the tree, and doing one without the
other leaves the document made of two kinds of thing for no reason.

## What it costs, and the part that is genuinely open

**The mounted route is the cost, and the demo is what pays it.** React cannot
render a physm node, so `<Scene>` as it exists today would not survive. What it
buys is worth naming rather than dismissing:

- a scene written as a component tree inside a React app, updating naturally
  when state changes — which is the **event regime**
  ([0016 page 2](0016/02-values.md)) working for free;
- context propagation for `FrameIdContext` and `ParentKeyContext`;
- hooks, for whatever a hand-written component wants them for.

The first is the one to think hardest about. The editor already gets the event
regime without React: the document changes, `buildScene` runs again. A game
could do the same — hold state, rebuild on change — and that is a function call
rather than a framework. So the question is whether mounting earns its keep once
the walk is the primary route, or whether it is a second way to do one thing.

**A middle answer exists** and should not be assumed away: physm owns the node
type, and a thin adapter renders a physm tree *into* React for anyone who wants
the mounted experience. That keeps the demo and confines React to a renderer,
which is where `SceneView` already lives.

## What has to be decided

- **Does physm own the element type?** Everything else follows from this.
- **Does the mounted route survive, and in what form** — deleted, or kept as an
  adapter over the owned node?
- **If it is deleted, does [0005](0005.md) close as "no longer reachable"?**
  That is a resolution rather than a fix, and it should be recorded as one.
- **What names a component in a node** — a registry key, which is what makes the
  node serializable and crossable, and which also bears on
  [0017](0017.md)'s `imported` ref and the frontier's long-standing
  want of a module rather than a function name. One answer may serve all three.

## Why it is filed before the expression work

[0016](0016.md)'s next built step is parameters, which touches the document
rather than the element type and is safe either way. The step after is
expressions — and an expression node built as a React element, then rebuilt as a
physm node, is the one sequencing mistake here that costs real work. Deciding
first costs a read; deciding later costs the expression system twice.
