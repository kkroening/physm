# 0019 — Decide what names a component, and whether physm owns its element type

**Status:** Open
· **Kind:** RFC
· **Parent:** <a href="README.md" title="Issues">Issues</a>
· **Related:** <a href="0016.md" title="0016 — Make the document a program rather than a drawing">0016</a>,
<a href="0005.md" title="0005 — Give JSX siblings their tree order, which effect registration cannot">0005</a>,
<a href="0017.md" title="0017 — Give the document a save format, since its own output cannot carry it">0017</a>

> `<RotationalFrame />` compiles to a `jsx()` call into `react/jsx-runtime`, so a
> scene tree is a tree of **React elements** that physm then interprets. Two
> questions come out of that, and they are not the same size. **What names a
> component** is small, ready, and wanted by four separate things. **Whether
> physm owns the element type** is large, and is really three decisions that can
> be taken apart — one of which genuinely needs the element type and two of
> which have cheaper answers already on record.

## What is true today

**A core component is two things bolted together**, and the seam is visible in
the source. `RotationalFrame` is a React function component whose body registers
into a context-provided registry:

```tsx
export default function RotationalFrame(props: RotationalFrameProps): ReactElement {
  const key = useId();
  const frameId = useContext(FrameIdContext);
  const node = describeRotationalFrame(props, { key, frameId });

  useSceneNode(key, node, { ...props, frameId });

  return (
    <ParentKeyContext.Provider value={key}>
      <FrameIdContext.Provider value={node.id}>{children}</FrameIdContext.Provider>
    </ParentKeyContext.Provider>
  );
}

RotationalFrame.sceneNode = describeRotationalFrame;
RotationalFrame.meta = { /* … */ };
```

The function body serves the **mounted** route. The `sceneNode` static serves
the **walk**: `buildScene` reads `type.sceneNode` and calls *that*, never the
component. So the walk already treats a core component as data — it calls only
*composites* as functions.

| route | who uses it | how a node is produced |
|---|---|---|
| mounted — `<Scene>` + `useSceneNode` | the demo (`App.jsx`) | React renders; effects register; the registry assembles |
| walk — `buildScene` | the editor | the tree is read; `type.sceneNode` is called directly |

`tsconfig.json` sets `"jsx": "react-jsx"`, the **automatic** runtime — so a tag
emits `jsx(RotationalFrame, …)` rather than `React.createElement`. Both return
an object carrying a `$$typeof` **symbol**; the difference matters only because
the two runtimes are configured by different knobs, and the automatic one's is
`jsxImportSource`.

## The small question: what names a component

A node records its component as a **function reference**. Nothing records where
that function came from, or a name stable under a production build. Four
separate things want the same missing fact:

- **[0017](0017.md)'s `imported` ref** — a saved document cannot name a
  component's module.
- **The frontier's long-standing want** of an imported component's tag coming
  from its module rather than from `Function.name`, which a minifier rewrites.
- **Worker transport** — a `type` holding a function cannot be structured-cloned
  at all.
- **`origins`** — the `WeakMap` keyed on element *identity* that the editor's
  picking depends on. Structured clone copies rather than preserves identity, so
  a map keyed on the originals resolves nothing that crossed a boundary. The fix
  is the same shape one level down: key it on something a copy still carries, a
  `NodePath` or the `rangeKey` the emitter already mints.

**This is nearly independent of what a tag compiles to.** A document could
record a stable component name and a module today, with React elements
unchanged. It is small, it has four beneficiaries, and it is the piece of this
RFC that looks ready to decide.

## The large question, which is three

"Should physm own the element type" bundles three decisions with different
answers. Separating them is most of the value of this page.

### 1. Representation — the one that genuinely needs it

An element carries a `$$typeof` symbol and a function in `type`. That is what
makes `emitScene`'s `literal()` refuse an element-valued prop, which named slots
([0016 page 6](0016/06-structure.md)) need.

**Scoped honestly, this buys less than it first appears.** Page 6 says named
slots are new work in *both* directions, and the reader half — descending into
an element-valued prop rather than only into `children` — has nothing to do with
whose element it is. Worse, a plain-object node makes `literal()` stop throwing
and **start succeeding**, writing `slot={{ type: "Box", props: … }}` where the
module needs `slot={<Box />}`: it would compile and build the wrong scene, where
today the emitter refuses and names the prop. So `writeNode` has to learn to
recognise a node in a prop either way — which is an argument for doing that work
*with* a node change rather than after it.

### 2. Assembly route — reachable without it

[0005](0005.md) exists because mounting orders siblings by registration, and
`buildScene`'s docstring says the walk has no such problem. It is tempting to
read that as evidence for owning the element type. It is not: **0005 records its
own answer, and that answer keeps React's element.**

> **A custom reconciler** is the mechanism that has this information: it is
> handed the tree and its order directly, rather than inferring order from the
> sequence effects happen to fire in. That was always the intended endpoint.

A reconciler is handed the tree, so it gets sibling order from the tree — while
keeping React's element type *and* the mounted route. 0005 also offers a cheaper
out: deciding that sibling order among conditionally-mounted nodes is
unspecified. Either resolves 0005 without this RFC.

### 3. Calling convention — also reachable without it

A hook resolves off the current dispatcher, which is a property of **who calls
the composite**. physm already owns that call site: `buildScene` calls a
composite directly, with a comment saying a hook there throws because there is
no dispatcher. So physm can export a `useState` that resolves against its own
context during the walk and delegates to React's when mounted — Karl's
wrap-rather-than-expose — and nothing about that needs the element type to
change hands.

## Keeping React's element

The option this page must not leave as an unstated default, since the
alternative gets an interface sketch below.

React's element is already serving. It gives context propagation for
`FrameIdContext` and `ParentKeyContext`; it gives the mounted route, which is
how the demo works and how the **event regime** ([0016 page 2](0016/02-values.md))
comes for free; and its two live problems have answers that do not need it
replaced — a reconciler for ordering, a physm dispatcher for hooks. What remains
is the representation: symbols and function references, which the emitter and
the worker both trip over.

So the honest form of the question is narrow: **is the representation worth a
JSX factory of physm's own, given that the other two legs have cheaper fixes?**

## What owning it would look like

`jsxImportSource` pointing at a physm runtime, so a tag produces:

```ts
interface PhysmNode {
  readonly type: string;        // a registry key, not a function
  readonly props: DocProps;
  readonly key?: string;
  readonly children: readonly PhysmNode[];
}
```

Plain data, serializable, no symbols and no function references.

**The cost is the mounted route, and the demo is what pays.** React cannot
render a physm node, so `<Scene>` as it exists would not survive.

**A middle answer exists**: physm owns the node type, and a thin adapter renders
a physm tree *into* React for anyone who wants mounting. That keeps the demo and
confines React to a renderer, which is where `SceneView` already lives — and it
shows that *owning the element type* and *the mounted route dying* were never
one question either.

## What would settle it

Not an argument, but evidence: **does anything other than the demo want the
mounted route?** If a game wants a scene that updates from React state, mounting
earns its keep. If the answer is that a game holds its own state and calls
`buildScene` on change — which is what the editor already does — then mounting
is a second way to do one thing.

That evidence does not exist yet and is not expensive to wait for.

## Why it is filed now, and what it is *not* urgent for

An earlier draft of this page argued that expressions would otherwise be built
as React elements and rebuilt as physm nodes. **That cannot happen**:
[0016 page 4](0016/04-expressions.md) decided that expressions are written as
constructor calls, explicitly declining JSX for them — *"calls are the right
spelling for expressions"* — so an expression node is a plain object either way.

What page 4's decision does leave is a real asymmetry: scene *trees* stay React
elements while expression *nodes* are plain data. Whether one document should
hold two representations is arguable, and the argument has to engage page 4's
reason rather than assume its absence — JSX earns its shape on trees and loses
it on `sqrt(add(pow(x, 2), pow(y, 2)))`, which is a reason, not an oversight.

So this is filed to be decided deliberately rather than urgently. The naming
question above is the part that looks ready now.
