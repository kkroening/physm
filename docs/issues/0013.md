# 0013 — Decide whether `stabilize` should default off, rather than leaving it defaulted

**Status:** Resolved
· **Kind:** RFC
· **Parent:** <a href="README.md" title="Issues">Issues</a>
· **Related:** <a href="0012.md" title="0012 — Give `physm-rs` its own stabilizer, so `RsSolver` need not step one at a time">0012</a>

> `Solver`'s `stabilize` flag defaults to `false`, and no caller and no test
> depends on that. Every test passes it explicitly in both directions and the
> demo passes `true`, so the default is currently the value nobody asks for —
> which makes it a decision nobody has made rather than one made and recorded.

## Background

Raised during review of [#23](https://github.com/kkroening/physm/pull/23), which
added projection stabilization.

The stated reason for defaulting off is that the unstabilized formulation is a
*diagnostic*: it is index-1, so `C(t) = C₀ + Ċ₀t` holds exactly, and that is
what distinguishes a drift caused by inconsistent initial velocities from one
caused by integration error. Any stabilizer erases the distinction, and there
are tests pinning it.

The counter-argument, from the review, is that the diagnostic is preserved by
those tests — all of which pass the flag explicitly — so the default is
protecting it from nobody. And the two failure modes are not symmetric:

- **A forgotten `stabilize`** looks correct for a minute and then the rig comes
  apart. That is precisely the bug report [#23](https://github.com/kkroening/physm/pull/23)
  was opened to fix, so the default reproduces it for anyone who does not know
  the flag exists.
- **A mistuned Baumgarte**, the alternative [`constraints.md` §7](../constraints.md#7-drift-and-how-it-gets-fixed)
  rejected, at least rings visibly.

There is a second-order point in the same direction. Much of the case against
Baumgarte is that an eventual interactive scene builder has nobody to choose its
two constants. A builder that has to know about `stabilize` is the same problem
one bit wide.

## Proposal

Pick one, and write down which:

- **Keep it off**, on the grounds that the default protects the diagnostic from
  a future caller who forgets rather than from the current tests. That is a real
  answer and it wants one clause in the docstring, because the docstring
  currently argues from the tests, which do not need it.
- **Flip it on**, so the safe configuration is the one you get by not thinking.
  `Solver.test.ts`'s two `off by default` assertions become `on by default`, and
  the handful of diagnostic tests gain an explicit `stabilize: false` — which
  they arguably want anyway, since they are *about* the unstabilized behaviour.

What this issue exists to prevent is the third outcome: the default staying `false`
because nobody revisited it, and the reasoning above being reconstructed from
scratch the next time somebody asks.

## Resolution

**Flipped on**, and the reasoning is now in `Solver`'s docstring and
[`constraints.md` §7](../constraints.md#7-drift-and-how-it-gets-fixed) rather
than here — the second half of the acceptance criterion, since a decision
recorded only in the issue that raised it is one the next reader has to go
looking for.

The deciding argument was the asymmetry, not the count of dependents: an
unstabilized rig looks right for a minute and then comes apart, which is quiet
and slow and looks like a modelling mistake, while stabilizing a scene that did
not need it costs a solve per step and shows up in a profile. The eventual
builder settles it — it assembles rigs with nobody to know the flag exists.

The diagnostic is kept where it belongs: the tests that rely on the unstabilized
behaviour now say `stabilize: false` explicitly, which is more legible than
inheriting it and survives the default moving again.

**One claim in the Background did not survive contact.** *"Every test passes it
explicitly in both directions"* was true of the stabilization tests and not of
the suite — four cross-validation arms and one drive test inherited the default.
Flipping it broke exactly one of them, and all five now state what they mean.

**Two coverage gaps surfaced on the way**, both from the observation that
nothing in the suite passed a `tickCount` above 1:

- `RsSolver`'s **batched wasm path** had no test at all, and the flip makes it
  the path the default no longer takes.
- The **stabilized per-step path with `tickCount > 1`** — which is precisely
  what the demo now runs — had none either.

Both are covered now, in one test with both arms, because the two failures are
different: a wrong count reaching wasm shows up unstabilized, and wrong loop
accounting shows up only when the loop actually iterates.

⚠️ **The default costs `RsSolver` its batched path** until
[0012](0012.md) puts the stabilizer on the Rust side — about 2× wall clock on
the demo rig. Accepted as the right side of the trade, not overlooked.

## Acceptance

`Solver`'s default is whichever of the two a human chose, and the docstring says
why that one — not which one it happens to be.
