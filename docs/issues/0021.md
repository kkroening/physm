# 0021 — Let a definition's parameters be reordered

**Status:** Open
· **Kind:** Enhancement
· **Parent:** <a href="README.md" title="Issues">Issues</a>
· **Related:** <a href="0016.md" title="0016 — Make the document a program rather than a drawing">0016</a>

> A definition's parameters appear as rows at the top of its tree, and can be
> added, edited, deleted and — since this issue was filed — moved by keyboard
> and toolbar. What they still cannot be is **dragged**, which every other row
> in that tree can, and which reads as an omission rather than as a rule.

## What is true today

`ParameterRow` handles the navigation keys, `Enter`/`Space`, `Escape`, `Delete`
and `Alt+↑`/`Alt+↓`. The toolbar's ↑ and ↓ move whichever kind of row the
selection is.

What it is not is a drag source or a drop target, and `TreeDrag` is still built
around a `NodePath` alone.

Order is not cosmetic. It is the order the emitted signature binds:

```tsx
function Pendulum({ bob, heft }: { bob: readonly [number, number]; heft: number })
```

so moving one changes the generated source, and a reader of that source reads
the declaration block's order.

## What has been done

**The keyboard and the toolbar.** `moveParameter(doc, definition, at, by)`
sits beside `removeParameter`, `Alt+↑`/`Alt+↓` on a parameter row moves it, and
the toolbar's ↑/↓ move whichever the selection is — a parameter's siblings
being the declaration block rather than a frame's children. It is a document
edit, so it undoes, and the selection follows the parameter rather than the
place.

One thing worth recording, because it is the sort of detail a second
implementation would get wrong the same way: a move that goes nowhere hands the
*same document* back rather than an equal one. The caller is a key being held
down, so running off the end has to mean nothing happened — and the editor
records one undo step per press, which would otherwise fill the history with
edits that changed nothing.

## What is left

**Drag.**

Drag is the larger half, and the reason this issue stays open.
`TreeDrag` is built around a `NodePath` — `dragging` is a path joined, and
`dropRefusal`, `dropPoint` and `onDropNode` all take paths — so a parameter
joining the same drag means either a second drag channel or widening that one
the way `Selection` was widened. Worth doing deliberately, and worth doing once
the declaration block holds more than parameters: [0016 page
3](0016/03-scope.md) has outputs, manipulators and force channels living there
too, and a drag that handles all of them is a different design from one that
handles parameters alone.

## A concept the drag work will want

Worth doing together, because the drag work needs it and would otherwise be the
third place to state the same thing badly.

The toolbar's ↑/↓ now read `selectedPath` *or* `selectedParameter`, resolved
afresh at each use site — a ternary per row kind. That is the shape `TreeDrag`
is already in one step further along: hard to extend because it is built around
a `NodePath` rather than around "a thing the tree can move". Something like
`movable(doc, focus, selection): { index, count } | null` would collapse both,
give the toolbar one thing to dispatch on, and subsume `movedParameter`.

It is deliberately **not** built yet. Designed now it would be designed against
two kinds; [0016 page 3](0016/03-scope.md)'s outputs and manipulators are what
would say whether "where the selection sits in whichever list holds it" is the
right cut or whether the list is the wrong unit entirely. Two arms beat an
abstraction guessed at from one example.

## What happens if the rest is not done

Very little now. Reordering works; what is missing is the gesture a person
reaches for after using the tree, which is inconsistent rather than blocking —
every other row in that tree can be dragged.

The original cost is gone: a parameter list used to be appendable only, with
delete-and-re-add as the sole way to change the order, and a reference refuses
that until the reference is given a value first.
