# 0026 — Hold the emitter's operation imports and the binding's exports together

**Status:** Resolved
· **Kind:** Bug
· **Parent:** <a href="README.md" title="Issues">Issues</a>
· **Related:** <a href="0016.md" title="0016 — Make the document a program rather than a drawing">0016</a>

> The emitter writes `import { mul, vec } from './react'` by collecting every
> operation name it finds in a document's props. The binding's re-export list
> is written by hand. Nothing holds the two together, so an operation the
> binding does not re-export is a module the emitter writes and nobody can
> compile.

## What is true today

`importsOf` derives the `core` set from the document itself — whatever
operations the props actually use — and emits them as one named import from
`./react`. `physm-js/src/react/index.ts` re-exports the operation constructors
by name, one line each.

The two lists agreed by coincidence rather than by construction: the binding
listed exactly the eleven keys of `OPERATIONS`, so every `Operation` was
importable. Adding a twelfth operation made them disagree for as long as it
took to notice, and nothing said so.

The emitter's own test harness *would* have caught it — `emitScene.test.tsx`
resolves `'./react'` to the real binding namespace and runs `tsc` over the
emitted source — but only for a document that uses the missing operation, and
no test document did.

## How it was closed

By two tests, in `emitScene.test.tsx` where the defect lives rather than beside
either list: every operation is re-exported by the binding, and no building
block is named like an operation — which would collapse the two into one
imported name.

**The objection above was right, and no new export was needed.** The first
attempt at this added an `operationNames()` to enumerate the table at run time,
and argued it was the sibling of `operationNamed()`. It was not: the parser
calls `operationNamed`, and nothing but a test would ever have called
`operationNames`. What the tests actually need is a literal written
`satisfies Record<Operation, true>` — which refuses a missing key and an
invented one, so `Object.keys` of it is an exhaustive enumeration the compiler
maintains, with nothing exported at all.

That is also what makes the loops non-vacuous, which they were not at first: a
runtime enumeration answering nothing passed them, and a loop sifting the
building blocks out of the binding by a marker could iterate zero times and
report green. Both now walk lists that cannot come back empty — the literal,
and `coreComponents`.

**The structural alternatives were weighed and not taken**, and are recorded
because the reasoning survives the fix:

- **Refuse in `importsOf`.** A `core` name the binding cannot supply is a
  document the emitter cannot write, and saying so names the operation. Honest,
  but it states the rule a third time rather than removing a statement of it.
- **Derive the re-export.** `export * from './../expression'` would be
  automatic and wrong — it would also publish `evaluate`, `computed`,
  `describe` and the rest, which are not part of what a scene module imports.

  A separate module holding only the constructors, re-exported wholesale by
  both, would make the two lists **one list**, and so is the only option here
  that removes the drift rather than noticing it. It is not taken because the
  constructors are not separable from the tables they are built from: `Operands`
  and `constructorFor` read `OPERATIONS` and `SIGNALS`, so the new module either
  imports from `expression.ts` and closes a cycle, or takes the tables with it —
  at which point it is not "only the constructors" and `expression.ts` is the
  module that has been hollowed out. A fourth module, re-exported by two others,
  to hold twelve one-line constructors costs more to read than the test costs to
  keep.
- **Emit from the core module instead.** The emitted import could name
  `physm-js/src/expression` directly, which is where the constructors are
  defined; then the binding's re-export is a convenience for hand-written
  code rather than a contract the emitter depends on.

The third is the one that keeps tempting, and the reason not to take it is that
the emitted module's shape is a thing a person reads: `react/index.ts` says in
as many words that the constructors are re-exported so "one import serves a
whole module", and splitting components from operations gives that up to fix a
list that a test can hold instead.

## How it was found

The review of the pull request that added the first signal operation, which had
deliberately withheld the binding's export. The withholding was reversed there
and the immediate divergence closed; this is the mechanism that let it happen,
which outlives that fix.
