# 0006 — Let a JSX rig be assembled without mounting a renderer

**Status:** Open
· **Kind:** RFC
· **Parent:** <a href="README.md" title="Issues">Issues</a>
· **Related:** <a href="0005.md" title="0005 — Give JSX siblings their tree order, which effect registration cannot">0005</a>

> `physm-js`'s selling point is that the scene graph needs no renderer: a
> `Scene` builds, steps and serializes in a worker, a test or Node. The new JSX
> way of *describing* a scene is the one way that does not. `<Scene>` assembles
> and draws, so getting a `Scene` out of a description means mounting a DOM
> renderer, sitting inside an `<svg>`, taking two renders, and receiving the
> result through a callback.

## Background

Raised as a design observation during review of
[#15](https://github.com/kkroening/physm/pull/15).

The cost shows first in that PR's own tests. `assemble()` wraps in `<svg>`,
drives `@testing-library/react`, and pulls the scene out of `onSceneChange`, to
obtain an object the imperative side gets from a constructor call. That is the
tax on every future test of the authoring half.

It also forecloses things that look natural from where the project is heading:
a scene definition shared with a worker, a JSX rig serialized by a Node script,
or a headless snapshot of what an interactive scene builder emitted.

**And it has a visible cost, found when the demo migrated to JSX**
([#22](https://github.com/kkroening/physm/pull/22)): registration happens in a
passive effect, which React defers until *after* the browser paints — so the
first painted frame shows an empty plot, and the scene appears on the second.
The scene used to be a module constant and was on screen in the first paint.
`App.jsx` already goes out of its way to avoid exactly this for the *view
transform*, using a layout effect so the miscentred first frame never reaches
the screen; the same reasoning now applies to the whole scene, with a larger
effect. A builder that assembled without waiting for a passive effect would
remove it.

## Proposal

Separate the two halves that `README.md` currently says "meet at `Scene`":

- a **builder** — `<SceneBuilder>`, or a `buildScene(element)` helper over a
  test renderer or `react-dom/server` — that registers and assembles and
  renders nothing;
- **`SceneView`**, unchanged, for drawing an assembled scene;
- **`Scene`** kept as the convenience that composes both, which is what the
  demo wants.

That also gives the two-render dance somewhere honest to live. A `buildScene()`
that flushes its own renders can return a scene *synchronously*, and callers
never meet `onSceneChange` at all — which is the API wart most likely to be
regretted, since it exists purely because a `Frame` takes its children as
constructor arguments.

## The counter-argument

Authoring being a React-only affordance is a defensible answer. The components
are React components; a scene described in JSX and never mounted is arguably
not a scene yet. If that is the position, it should be stated in
`sceneNodes.ts` next to the three other consequences of the design that are
already written down there — not left as an accident of `Scene` doing two jobs.

## Acceptance

Either a scene can be assembled from JSX without a DOM renderer, or the
docstrings say plainly that it cannot and why. Deciding before `App.jsx` and
anything else is written against `<Scene>`: this is cheap now and a breaking
change later.
