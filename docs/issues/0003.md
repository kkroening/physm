# 0003 — Decide whether `Decal.xform` or the renderer is the real transform API

**Status:** Open
· **Kind:** RFC
· **Parent:** <a href="README.md" title="Issues">Issues</a>
· **Related:** <a href="0004.md" title="0004 — Place a solid box's rect from its corners rather than assuming a y-flipping view transform">0004</a>

> Every decal transforms itself twice, by two different routes, and only one of
> them has a caller. `Decal.xform(m)` returns a new decal in transformed
> coordinates; the decal views in `src/react/` transform the geometry inline.
> Nothing outside the test suite calls `xform`.
>
> That was true before the renderer moved out, since `getDomElement` never
> called `xform` either. What changed is that the pair is now split across the
> core/renderer boundary rather than sitting in one file, which is a worse place
> for it. This issue is to pick one.

## Background

Raised during review of [#14](https://github.com/kkroening/physm/pull/14), which
moved rendering out of the scene graph.

`git grep '\.xform(' physm-js/src` returns four hits, all in tests:
`BoxDecal.test.ts`, `CircleDecal.test.ts`, `LineDecal.test.ts` and
`Weight.test.ts`. Nothing in `Scene`, `Frame`, `App` or either solver calls it —
so `xform` is exercised only by tests that exist to exercise it.

Meanwhile `BoxDecalView`, `CircleDecalView` and `LineDecalView` each apply the
transform to the geometry directly, which is the code that actually draws the
picture.

The two are not trivially interchangeable, which is what makes this a decision
rather than a cleanup. `BoxDecal.xform` reconstructs a box from transformed
`width`, `height`, `position` and `angle`; the renderer carries the precomputed
`corners` through the matrix. Those agree only for a rotation and a uniform
scale — a reflection, which is what a y-down screen transform is, composes into
`angle` wrongly. `BoxDecal.corners` is public precisely so the renderer can take
the exact path.

## The two coherent answers

**`xform` is the API.** `DecalView` calls `decal.xform(xformMatrix)` and reads
the already-transformed geometry off the result, so "how a shape moves" stays in
the core with the rest of the geometry and the duplication collapses.

- Costs an allocation per decal per frame per draw.
- Puts `BoxDecal.corners` back behind the class, which means fixing
  `BoxDecal.xform` to be exact under reflection first. [0004](0004.md)
  describes that problem but **did not fix it** — it resolved the *renderer*
  side by drawing the corners directly, and left `xform` as it was.

**The renderer is the API.** `xform` is dead weight; delete it and its three
tests.

- Simpler, and matches where the description/instance split is heading: a decal
  becomes plain data and every operation on it lives outside the class.
- Loses a genuinely useful operation if anything later wants to bake a transform
  into a scene description (flattening a subtree, exporting).

The reviewer leaned toward deleting. That looks right, but it is a call about
what a "description" is, so it belongs with that work rather than ahead of it.

**[0004](0004.md) sharpened the argument for deleting.** The renderer now draws
every box from its transformed corners, so no rendering path derives one from
`width`, `height` and `scaleFactor` any more — `BoxDecal.xform` is the last
place that construction survives. And `BoxDecal.test.ts` pins it with
`mat3.scaling(5, 5)`: a rotation and a uniform scale, which is exactly the
family where the two routes agree and the difference cannot show.

## Acceptance

Either `DecalView` routes through `xform`, or `xform` and its tests are gone —
and whichever survives is the one the next decal kind has to implement.
