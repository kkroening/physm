# 0010 — Make a dead export a build signal rather than an eyeball finding

**Status:** Resolved
· **Kind:** Enhancement
· **Parent:** <a href="README.md" title="Issues">Issues</a>
· **Related:** <a href="0008.md" title="0008 — Delete `testutils.ts`, which nothing imports and the lint config misnames">0008</a>

> Nothing in the toolchain can see an exported symbol with no importer. Both
> unused-variable rules report unused *locals*, and `noUnusedLocals` is off in
> `tsconfig.json` and would not cover it anyway. So a module can survive with no
> consumer indefinitely, and the only thing that finds it is somebody reading.

## Background

Raised during review of [#20](https://github.com/kkroening/physm/pull/20).

`testutils.ts` outlived its last consumer, survived the TypeScript port, and was
eventually noticed by eye while auditing an unrelated lint entry. CI was green
throughout, and could not have been otherwise.

There is no backlog behind it — the reviewer checked, and every other module
under `physm-js/src` has at least one importer, with all four of `utils.ts`'s
exports reached. So this is about the next one.

It bears on something `CLAUDE.md` already describes as in progress: `utils.js`
being dismantled a piece at a time. Dismantling is exactly the process that
leaves orphans, and `testutils.ts` was one of them.

## Proposal

A dead-export check as a lint step — [`knip`](https://knip.dev) or
[`ts-prune`](https://github.com/nadeesha/ts-prune). `knip` is the more current
of the two and also reports unused files and unused dependencies, which is the
same class of finding.

Two things worth deciding rather than assuming:

- **Where it runs.** CI as its own step, beside the format check, matches how
  the other conventions ended up enforced ([0001](0001.md)).
- **What counts as a false positive.** An export used only by tests, an entry
  point, and a type re-exported for a consumer that does not exist yet are all
  legitimate. A check that has to be argued with every time is one that gets
  removed.

## Acceptance

Deleting the sole importer of any module makes a CI job fail rather than
producing a green build and a file nobody reads.

## Resolution

`knip` runs as its own CI step beside the lint and format checks, and as
`npm run lint:dead` locally. The acceptance above was tested rather than
assumed: a module that nothing imports turns the step red with
`Unused files (1)` and exit 1, and removing it turns it green.

**Everything knip checks by default is in scope** — files, dependencies,
exports, types, duplicates — and the tree is clean of all of it, so the config
is a single `ignoreBinaries` entry for `wasm-pack`, which knip cannot find
because it does not consult `PATH`.

Getting there took un-exporting twelve symbols that were referenced only inside
their own modules: `consistencyTolerance`, `planarDeterminant`,
`isValidStateMap`, `SingularCorrectionError`, `daglet`'s two default callbacks,
its four exported types, `AnyComponent` and `PropKind`. Over-exported rather
than dead, and each was dispatched by removing the keyword and letting the
type-checker and the suite say whether anything needed it. Nothing did.

**Counts quoted here are knip 6's.** Which findings exist is a property of the
tool as much as of the tree: knip 5 reported fifty-one unused exports on this
same tree, forty-five of them React props interfaces, because it does not
attribute a type used in a used export's signature to that export. A major bump
is the moment to re-run and re-read rather than to take the green tick.

**What the step does not see** is a module kept alive only by its own test.
knip treats a test file as an entry point, and 39 of the 68 modules under
`src/` have a sibling test — so for those, a green step means "not even its own
test imports this". `testutils.ts`, the module that prompted this issue, had no
test and would have been caught; the next one may not be. Closing that needs a
production-scoped pass, which is <a href="0015.md" title="0015 — Decide whether physm-js declares a surface, and run the dead-code check against it">0015</a>.

Two dependency findings were real and are fixed here: `@eslint/js` was imported
by `eslint.config.js` without being declared, and `@testing-library/user-event`
had no importer at all.
