# 0023 — Run a real mutation tester, instead of enumerating mutants by hand

**Status:** Open
· **Kind:** Enhancement
· **Parent:** <a href="README.md" title="Issues">Issues</a>

> Every change of consequence here is checked by mutating the code by hand and
> watching the suite fail. It works — it has caught real gaps — but the
> enumeration is a list somebody wrote, so it reports what they thought of. Over
> seven review rounds it has missed something in **five distinct ways**, and
> every one of them would have been found by a tool that mutates everything.

## What is done today

By hand: pick a mutation, apply it as an exact-string replace, run the suite,
restore, repeat. A count goes in the PR description.

The findings it produces are real. The failures of it are systematic, and they
are failures of *enumeration* rather than of method:

| what was missed | round |
| - | - |
| Mutants only in files that already had tests, so none reached new code | #74, #81 |
| Mutants that change a value's **type** but never its **range** — `!== 2` → `< 2`, dropping `Number.isFinite` | #85 |
| Mutants killed by `tsc` counted as evidence about the *tests* | #86 |
| Every file in the diff but the one thought of as "the subject" | #87 |
| Fixes made in response to a review finding, where the finding felt like the verification | #86 |

Five categories, each learned from a defect that reached review. A sixth is
presumably waiting.

**The common cause is not carelessness.** A hand enumeration is written by the
same person who wrote the code, in the same frame, immediately afterwards. It
covers what they were thinking about. The parts they were *not* thinking about
are exactly the parts a mutation score exists to find.

## What a tool changes

[Stryker](https://stryker-mutator.io/) mutates every statement, operator,
boundary and literal it can reach, and reports which survived. It does not have
a frame.

- **Every file in the diff is covered**, by construction rather than by
  remembering.
- **Boundary and range mutants come free** — `<` to `<=`, `!==` to `===`,
  removing a condition — which is one of the five categories on its own.
- **A survivor is a fact rather than a claim.** A PR description could carry a
  score that a reader can check, rather than "twelve mutants, all killed",
  which is unauditable and has twice been true while being misleading.

## What it costs, honestly

- **Runtime.** A full run mutates the whole tree; incremental mode and
  `--since` keep a PR's run to the files it touched, and this repo's suite is
  ~4s, so the per-mutant cost is small. Worth measuring before committing to a
  CI gate.
- **A threshold is a policy decision.** A score gate that is too high makes
  people write tests for equivalent mutants, which is worse than no gate. A
  report with no gate is still most of the value.
- **Equivalent mutants** exist and always will — two have already turned up by
  hand here ([#84](https://github.com/kkroening/physm/pull/84)'s no-op
  refactor, [#87](https://github.com/kkroening/physm/pull/87)'s dead fixpoint
  pass). A tool produces more of them, and reading them is the cost.

## What this does not replace

Reading. Three of the seven rounds' most valuable findings were not
mutation-shaped at all: a claim in a doc that the code did not support, a guard
that existed and did not cover its own case, a picture that lost information
placement rather than by comparison. A mutation score would have said nothing
about any of them.

So this is a floor, not a ceiling — and the argument for it is precisely that
the floor is currently being laid by hand, by the person least able to see where
it has gaps.

## Open question

**Whether it gates CI or only reports.** Reporting is cheap and immediately
useful. Gating needs a threshold, and a threshold needs a baseline that nobody
has measured yet. Karl's call, and worth deciding after one run rather than
before.
