# 0028 — Decide how a signal is written in the editor

**Status:** Open
· **Kind:** RFC
· **Parent:** <a href="README.md" title="Issues">Issues</a>
· **Related:** <a href="0016.md" title="0016 — Make the document a program rather than a drawing">0016</a>,
<a href="0022.md" title="0022 — Decide whether the parameter types grow toward the prop kinds">0022</a>,
<a href="0025.md" title="0025 — Decide whether the expression language has exponentiation">0025</a>

> A `<WorldLine>` draws a line between two points on different bodies, and the
> only way to say which two points is to hand-write TSX. The plan said the
> editor's half was small — a `PropSpec` saying which kind a property admits,
> and the prop box narrowing its refusal to read it. It is not, and the reason
> is worth writing down before anyone starts on it.

## What is true today

[0016 page 2](0016/02-values.md) says the editor should refuse the wrong kind
"at the point of typing rather than at the point of running", and the prop box
does — unconditionally, since no `PropSpec` says a property admits one.
Narrowing that to read a spec is a few lines.

A property that admits one already exists: page 2's own table says a world-space
decal's endpoints are signals, and `buildScene` hands a `<WorldLine>` its props
*unfolded* so that one survives to the draw. A document holding a
`worldPoint(...)` in `startPos` builds and draws through the editor's own route
today.

It would also change nothing observable, because a person cannot type a signal
in the first place. Two independent reasons:

- **A point property is not offered as text.** `TYPED_TEXT` in
  `PropertiesPane` is `{ number, length }`. A point is edited as two numeric
  fields, and a `<WorldLine>`'s endpoints are points — so there is no box to
  type an expression into, whatever the spec says.
- **The grammar cannot write down an id.** `parseExpression`'s primary is a
  number, a name, a call, or a parenthesised expression — there is no string
  syntax, and `'` is not even a token. `worldPoint`'s first operand is a frame's
  id, so no text produces it.

  The *point* half is already reachable, which is worth being precise about
  because it halves an option below: `worldPoint('cart', vec(0, 0))` is a
  well-formed graph today, since `vec` is an ordinary operation, a call parses,
  and operands are folded before `worldPoint` sees them. A `[0, 0]` literal
  would be an ergonomic improvement competing with a spelling that works, not a
  blocker.

So the `PropSpec` admission is a no-op until both of those move, and each is a
question rather than a chore.

## The question under the chore

**Should a frame id be typed at all?**

An id is a string a person can get wrong, and the editor is the one party that
knows which ids exist. Page 2's own example is a line "between two anchors" —
and an anchor is already a first-class named thing in this editor, with a
registry, a refusal for duplicates, and constraints that name one.

That suggests the editing surface for a signal might not be text at all:

- **Grow the grammar** — a string literal, and point properties become
  text-editable. Uniform: everything a document can hold, a person can type.
  It also makes a typo in a frame id a refusal at *run* time rather than at the
  point of typing, which is the thing page 2 wanted to avoid.
- **Pick it** — the endpoint field offers the anchors and frames the scene has,
  and writes the node. A picked id cannot be a typo, and the field can show a
  name rather than a quoted string.

  **This is not the cheap option, which is the correction worth having before
  choosing.** `worldPoint(frame, local)` wants both halves as values, and an
  `<Anchor>` may deliberately have no point — the absence is what says "solve
  for this attachment", and `CartAndRope`, which is page 2's own picture, uses
  both forms: `left-tip` states its point and `right-tip` does not. The frame
  half is no better where anchors matter most, since a `RopeSegment`'s frames
  declare no id — the reason `<Anchor>` exists. And anchors do not survive
  assembly at all: `assembleScene` consumes them into constraint ends, so a
  running `Scene` has nothing named `right-tip` to ask.

  So a picker cannot generally write a `worldPoint` node. It wants either a
  second signal that names an anchor and resolves after the solve, or anchors
  surviving into the scene — both core work rather than editor work. That may
  be the right answer anyway: it suggests what a person picks is an *anchor*,
  and that the leaf the editor writes is not the leaf a hand-written component
  writes.
- **Both** — the picker is the affordance and the grammar is the fallback, the
  way a colour field has a swatch and a hex box.

  It inherits the first option's drawback rather than escaping it: a typo typed
  into the fallback lands at run time exactly as it would have. So choosing this
  means holding that a fallback path's typos are acceptable where a primary
  path's are not, which is the swatch-and-hex bargain made explicit.

**The editor already runs the third arrangement, for constraint ends.**
`PropField`'s `end` case is a typed box with a `datalist` of every anchor and
frame id in the document — the same id set an endpoint picker would offer — and
its comment records the trade already made there: *"Offered, not enforced: an
end naming nothing yet is an ordinary state of a rig being written, and the
scene pane says so."*

That is evidence in two directions, and it is left as evidence rather than
argued from. It lowers the id half of "the most work", since the arrangement
exists over the right names. And it shows that page 2's "at the point of typing"
has already been traded away once here, deliberately and with a reason — for a
value in the same namespace — which is worth weighing against treating it as the
constraint that decides between the options.

## Why it is filed rather than decided

It is a question about what the *editing surface* is, which is Karl's, and it
touches the same ground as [0022](0022.md) (do the parameter types grow toward
the prop kinds) and [0025](0025.md) (what arithmetic there is). Those two are
already waiting on one answer between them; this is the third, and it is the one
with a concrete feature behind it.

## What happens if this is not done

`<WorldLine>` stays reachable from hand-written TSX and unreachable from the
editor. It can be inserted, moved and given literal endpoints there — a fixed
line in world space — but not pointed at a body, which is the thing it is for.
