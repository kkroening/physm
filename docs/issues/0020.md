# 0020 — Carry a parameter across an extraction, instead of refusing one

**Status:** Open
· **Kind:** Enhancement
· **Parent:** <a href="README.md" title="Issues">Issues</a>
· **Related:** <a href="0016.md" title="0016 — Make the document a program rather than a drawing">0016</a>

> Extracting a subtree into a component of its own is a **pure document edit**:
> the scene it builds is unchanged. A node whose prop refers to a parameter
> breaks that, because the new component declares no parameters — so the
> reference would resolve against an empty scope and the prop would quietly fall
> back to the component's own default. Extraction refuses such a subtree today.
> Carrying the declaration across instead is the better answer, and it wants
> machinery that does not exist yet.

## What is true today

A definition declares typed parameters; an instance passes literals; a child
prop may hold a reference to one, which `elementOf` resolves against the scope
the instance supplied.

`extractComponent` moves a node and everything under it into a new definition,
leaving an instance behind. It copies `node.props` across whole, and the new
definition gets no `parameters`. `extractionRefusal` therefore refuses any
subtree holding a reference, naming the prop:

> `Weight's position refers to Scene's bob, which a component of its own would
> not take: extracting it would change the scene. Give it a value first.`

The refusal is correct and cheap, and it is the right thing until there is
something better. It is also a real limit: the more a document uses parameters,
the more of it cannot be refactored.

## What carrying it would mean

Three steps, none hard on its own:

1. **Collect** the parameter names the subtree refers to — every `parameter`
   prop under the node, deduplicated.
2. **Declare** them on the new definition, copying each declaration (type and
   default) from the definition being extracted *from*.
3. **Thread** them: give the instance left behind a `parameter` prop per name,
   so the enclosing definition's argument reaches the extracted component
   unchanged. That is what keeps the scene the same.

Step 3 is the one that matters, and it is also the one that says when to build
this: it is **promote to prop pointed the other way**. Promote-to-prop turns a
literal already on a node into a parameter plus a reference to it; this turns a
reference on a node into a parameter of a *new* definition plus a reference from
its instance. The two want the same edit primitive, and building it twice would
be the wrong trade — which is why the refusal stands for now.

## Open questions

- **A name the destination already declares.** Extracting into a name that
  exists is not possible today (a new definition is always new), so this only
  arises if extraction ever gains a "into an existing component" mode.
- **A reference whose parameter has no default.** The instance left behind
  supplies it, so the extracted component can declare it without one — but its
  own tab then builds with the parameter unresolved, which is the same state a
  definition tab is already in for any parameter without a default. Worth
  deciding once, for both.

## What happens if this is not done

Nothing breaks. The refusal keeps the invariant; a person who wants the
extraction replaces the reference with a value first, extracts, and wires the
parameter back by hand.
